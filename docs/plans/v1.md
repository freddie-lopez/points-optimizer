# Build plan: Points transfer optimizer (v1)

**Author**: Architect
**Date**: 2026-09-08
**Baseline**: v0 shipped. 118 tests pass. Chase UR only, flights-first, cash
fallback at 1cpp, provenance model in place.
**Scope chosen by Tsuki**: hotels properly, multi-currency (MR / TY / C1 / Bilt),
surcharge modeling. Personal-tool-vs-product decision **deferred** until a real
margin number exists.

---

## 1. Summary

v0 answers one question: *given a Chase UR balance, should I transfer or pay
cash?* It answers it structurally wrong in three places, and v1 fixes exactly
those three.

1. **It cannot see carrier-imposed surcharges**, so it scored two British
   Airways legs at $0 YQ and produced a 16% headline that is probably ~7%. The
   fix is not "add a surcharge column" — surcharges are a function of
   **program × operating carrier metal × route region × cabin × departure
   country**, which means the tool must model the *metal*, not just the program.
2. **It knows one currency.** Half of the transfer landscape (Hilton, Accor,
   Turkish, Avianca, Choice, and every Amex/Citi/C1/Bilt-only partner) is
   invisible, so "no points path" sometimes means "no path from UR".
3. **It treats hotels as cash-only legs with a break-even footnote.** It has no
   concept of a per-night award price, and no concept of the mandatory fees that
   are owed *even on a points stay* — the same class of bug as the missing YQ.

v1 builds capability, not product. No accounts, no OAuth, no billing, no
multi-user, no hosting. The deliverable is a CLI that, run on Tsuki's Mac with
his real wallet, produces a defensible margin number — the number that decides
whether this is a personal tool or a product.

The single sentence v1 must be able to say and v0 structurally could not:

> **"Same flight, same 20,000 Avios — book it through Iberia instead of British
> Airways and pay $400 less cash."**

## 2. Assumptions & decisions

### Settled — do not re-derive

- **Chase UR ratios are verified.** All 14 partners 1:1, except World of Hyatt:
  Sapphire Reserve 1:1 always; Sapphire Preferred and Ink Business Preferred
  drop to 4:3 on 2026-10-01. The October change is **Hyatt-only** and touches no
  airline. `data/ratios.csv` is correct as shipped. Do not re-research it.
- **Surcharges are program × operating carrier, not program alone.** The
  research is done (§7 of this plan holds the seed table). Do not re-research
  it; do verify anything you are about to present as a confirmed dollar figure.
- **`data/bonuses.csv` stays empty.** No current bonus has been verified.
  Inventing a 25% promo silently inflates every downstream result. The bonus
  *mechanics* are tested against `tests/fixtures/bonuses_test.csv`, labelled
  SYNTHETIC. This does not change in v1.

### New decisions for v1

- **The wallet is runtime input, never a constant.** Balances *and* card
  holdings come from a `--wallet` JSON file or CLI flags. Nothing about which
  cards Tsuki holds is compiled into the tool or into any data file. A missing
  currency is absent, not zero, not assumed.
- **Absence of a surcharge row means UNKNOWN, never $0.** This is the single
  most important rule in v1 and it is the direct inverse of the v0 bug. An
  unknown surcharge produces a **break-even surcharge** ("points win only if YQ
  is below $X"), exactly parallel to v0's break-even-points behaviour.
- **Surcharge estimates are ranges, not points.** Every modeled row carries
  `low` / `point` / `high`. If the verdict flips anywhere inside the range, the
  leg is flagged **verdict-sensitive** and the tool refuses to present the
  recommendation as settled.
- **Captured beats modeled beats unknown.** A surcharge read off a real booking
  page or returned by Seats.aero always overrides the table. Provenance is
  carried through to the output, same as v0's points provenance.
- **The transfer date is not the travel date.** v0 looks up ratios on
  `leg.date`. That is wrong: the ratio that applies is the one in force **when
  you transfer**. Today is 2026-09-08; the Hyatt 4:3 change lands 2026-10-01;
  the real trips travel January 2027. v0 would quote 4:3 for a transfer Tsuki
  could make at 1:1 *this month*. v1 separates `--transfer-date` (default:
  today) from travel date, and surfaces "transfer before 2026-10-01 to keep 1:1"
  as an actionable finding.
- **Points across currencies cannot be summed.** `TransferPath.total_points_cost`
  adds source points across programs. Its own docstring concedes this is only
  faithful because every UR ratio in scope is 1:1. With five currencies at
  differing ratios it becomes a category error. v1 scores every funding plan in
  **USD** at a per-currency valuation (all default to 1cpp — the same neutral
  yardstick), and reports the raw per-currency amounts separately. A single
  cross-currency points integer is removed from the ranking path.
- **v1 does not find hotel awards.** There is no public award-rate API for
  Hyatt / Marriott / IHG / Wyndham, and Seats.aero is flights-only. v1
  **evaluates hotel awards the user brings**: the user reads the points price
  off the hotel site and supplies it. Stated plainly in the README and in every
  hotel row of the output. Do not build anything that implies otherwise.
- **Seats.aero remains unverified until proven otherwise on Tsuki's Mac.** See
  Step 0. No live number is trusted before that gate passes.

## 3. Out of scope for v1

- User accounts, login, signup, billing, OAuth, multi-user, hosting, any
  productization. **Explicitly deferred by Tsuki** pending a real margin number.
- **Hotel award search.** No API exists. Manual entry only (see §4.5).
- **Award chart modeling.** v1 never computes what an award *should* cost in a
  program. It consumes prices from Seats.aero or from manual capture. Modeling
  15 award charts is a v2 question and would be the largest single source of
  invented numbers in the codebase.
- Scraping airline, hotel, or issuer sites.
- Card-linked offers, 5/24, application eligibility, signup-bonus modeling.
- Positioning-flight solving (MRY↔SFO/SJC stays unpriced input, as in v0).
- Live FX fetching (still config; §Step 12 tightens the placeholder handling).
- Interactive GUI. CLI plus the existing HTML export.
- Elite status, upgrade instruments, companion certificates, Avios combining
  mechanics (flagged in §11 as a known unmodeled interaction).

### 4.2 Data model additions

**Operating carrier is now first-class.** v0's `Award.airline` is ambiguous
(marketing or operating?) and `PointsCandidate` has no carrier at all. That
ambiguity is precisely what hid the BA surcharge.

```python
@dataclass
class PointsCandidate:          # extended
    ...                          # all v0 fields retained
    operating_carrier: str = ""  # IATA of the METAL, e.g. "BA", "IB", "EI"
    marketing_carrier: str = ""  # who sells it; may differ
    carrier_source: str = "unknown"   # "seats_aero" | "captured" | "assumed"
    cabin: str = "Y"                  # Y | W | J | F
    is_round_trip: bool = False
    surcharge: Optional[SurchargeEstimate] = None   # resolved at evaluation time
```

`operating_carrier` empty or `carrier_source == "assumed"` degrades the
surcharge result to UNKNOWN. **The tool never guesses metal.**

```python
@dataclass
class SurchargeEstimate:
    amount_low: float
    amount_point: float          # what we score with
    amount_high: float
    currency: str
    basis: str                   # "round_trip" | "one_way" | "per_segment"
    confidence: str              # "captured" | "modeled" | "unknown"
    matched_rule: str            # which surcharges.csv row fired, for explainability
    source: str
    verified_on: Optional[date]

    @property
    def is_known(self) -> bool:
        return self.confidence != "unknown"
```

```python
@dataclass
class MandatoryFee:
    """Cash owed regardless of how the booking is paid for. The hotel analogue
    of a carrier surcharge, and the same bug shape: v0 stored this as free text."""
    label: str                   # "Marriott destination fee", "Amsterdam city tax"
    amount: float
    currency: str
    per: str                     # "night" | "stay" | "person_night"
    payable_on_points: bool = True
    source: str = "captured"
```

```python
@dataclass
class FundingPlan:
    """Replaces TransferPath as the ranking unit. Multi-currency aware."""
    transfers: List[Transfer]
    existing_target_points_used: int
    per_currency_spend: Dict[str, int]      # source points by currency
    delivered: int
    stranded_points: int                    # destination currency
    ratio_remainder_points: Dict[str, int]  # source points lost, by currency
    score_usd: float                        # per-currency cpp, summed in USD
    currencies_used: int
    feasible: bool
    infeasible_reason: str
    reasons: List["Reason"]
```

```python
@dataclass
class Reason:
    """Typed, machine-checkable explanation. Tests assert CODES, not prose,
    so the explanations can be reworded without breaking the suite."""
    code: str      # RATIO_CHOSEN | CARD_CHOSEN | SURCHARGE_MODELED |
                   # SURCHARGE_UNKNOWN | SPLIT_REQUIRED | STRANDING_REJECTED |
                   # DEDUP_DROPPED | VERDICT_SENSITIVE | TRANSFER_DATE_WINDOW
    detail: str
    data: Dict[str, object]
```

### 4.3 The surcharge model

`data/surcharges.csv`:

```
program,operating_carrier,route_region,cabin,departure_country,
amount_low,amount_point,amount_high,currency,basis,confidence,source,verified_on,notes
```

**Lookup is most-specific-wins**, in this fixed order. The first tier that
matches wins; no averaging, no blending:

1. `(program, carrier, region, cabin, departure_country)`
2. `(program, carrier, region, cabin, *)`
3. `(program, carrier, region, *, *)`
4. `(program, carrier, *, *, *)`
5. `(program, *, *, *, *)` — **legitimate only for a blanket program-wide
   no-YQ policy** (United, Aeroplan on partner awards). A wildcard row for a
   program that *does* levy YQ is a data bug and Step 7's validator rejects it.

**No match → `confidence="unknown"`.** Never zero. Never a neighbouring row.

`route_region` is a normalized unordered pair from `regions.py`, e.g. `NA-EU`,
`NA-NA`, `EU-EU`, `NA-AS`. `departure_country` exists to capture UK APD, which
stacks on top of the carrier surcharge and makes ex-LHR the worst case in the
whole model.

**Basis conversion.** The research is expressed round-trip. A one-way leg
matched against a `round_trip` row is halved and tagged
`SURCHARGE_BASIS_CONVERTED` — an approximation, disclosed every time, because
real surcharges are directional and are not symmetric out of the UK.

**Cabin.** The research figures are business-cabin. Economy rows are **not
extrapolated** — that would be inventing numbers. The exception is programs with
a structural no-YQ policy (United, Aeroplan, KrisFlyer on own metal), where zero
is a program rule rather than a cabin-specific figure and a `cabin=*` row is
correct. Consequence, and it is the right one: **Tsuki's economy BA legs resolve
to UNKNOWN and report a break-even surcharge**, while the Aeroplan/United
alternative resolves to a confirmed $0. That comparison is still decisive, and
nothing was fabricated to get it.

### 4.4 Multi-currency search: keeping it tractable

The stated fear is path explosion: 5 currencies × ~14 partners × cards ×
date-scoped bonuses. In practice the search is **candidate-driven, not
enumeration-driven**, and that is what keeps it small.

We never enumerate "all reachable programs". We start from **priced award
candidates** — each candidate already names its program, so the question is only
*"what is the cheapest way to fund program P from this wallet on the transfer
date?"* For a given P:

- only currencies that partner with P matter — typically 1–3 of 5, never all;
- for each such currency, `best_ratio_across_cards()` already collapses cards to
  a best-first list (v0, bug #1 fix);
- bonuses are a multiplier on an already-chosen ratio, not a branch.

Per leg the cost is `O(candidates × currencies × cards)`. With 8 candidates, 5
currencies and 4 cards that is 160 evaluations — microseconds. **The explosion
never materialises because we refuse to price awards we have no price for.**

The one genuinely combinatorial piece is **split funding** (§4.6), bounded to
pairs: `C(5,2) = 10` combinations per candidate.

**Deduplication.** Collapse to the cheapest plan per
`(leg_id, target_program, operating_carrier, cabin)`. Then, across survivors,
keep everything **Pareto-optimal on `(points_score_usd, cash_out_of_pocket)`** —
not just the single cheapest. This is what surfaces the headline case: the
Iberia option is not cheaper on the combined score by much, but it is
dramatically better on cash-out-of-pocket, and a user who is points-rich and
cash-poor wants to see it. Dropped options record a `DEDUP_DROPPED` reason so
"why didn't it show me X" is answerable.

**Explainability.** Every surviving plan carries an ordered `List[Reason]`.
The formatter renders them; the tests assert reason codes. No plan may reach the
output without at least one reason explaining its ratio and its surcharge state.

### 4.5 Hotels, properly

"Properly" means four concrete things, none of which is award search.

1. **Per-night award pricing.** A stay is `nights × points_per_night`, or a
   captured total. Standard award, off-peak/peak, and points+cash are all
   candidate types; points+cash uses the existing (points, cash) pair.
2. **Mandatory fees are modeled, not noted.** Destination fees, resort fees,
   city tax, mandatory parking. These are owed **on a points stay too**, so they
   belong on the *leg*, not on the cash option — v0 put them on `CashOption` as
   a free-text string, which meant they never entered a single total. Structured
   `MandatoryFee` with `per` and `payable_on_points` fixes it. The Marriott
   destination fee and the €56.47 NH Amsterdam city tax from the real trip are
   the two live examples.
3. **Award rules are data, off by default.** Fifth-night-free, award-stay tax
   treatment (points stays in some jurisdictions are taxed differently), and
   category/peak calendars go in `programs.yaml` as per-program flags that
   **default to off and require a source and a `verified_on` date to enable**.
   Shipping them off is capability without invention.
4. **Manual entry is the documented input path.** A `hotel` leg accepts
   `points_candidates` with `program`, `points_per_night` or `points_total`,
   `mandatory_fees`, and a `source` that will read `manual_capture`. The README
   and every hotel output row say: **v1 does not find hotel awards; it evaluates
   ones you bring.**

### 4.6 The stranded-points rule, restated for multi-currency

v0's rule — *strand no more than one indivisible transfer block* — is correct
and survives. Multi-currency needs three additions, stated precisely:

- **R1. Stranding is a property of the plan, not of a transfer.**
  `stranded = total_delivered - points_needed`, measured in the destination
  currency, summed over every transfer in the plan.
- **R2. Only one transfer in a plan may carry rounding slack.** Construct plans
  so that every currency but the last is sized to an exact increment multiple
  that *under*-fills, and the last currency covers the remainder rounded up.
  The ceiling therefore stays **one block**, not the sum of blocks:
  `ceiling = max over transfers of (destination points per source increment) - 1`.
  A naive implementation that rounds each currency up independently would strand
  up to N blocks and would silently pass v0's test suite. This is the most
  likely place for a subtle regression — Step 5's tests target it directly.
- **R3. Do not split when a single currency will do.** A split is permitted only
  if (a) no single currency can fund the award within its balance and ceiling,
  or (b) the split is strictly cheaper on the USD score. Ties break to **fewer
  currencies**. Splitting creates unusable residue in two accounts and doubles
  the operational risk of a one-way transfer.
- **R4. `MAX_SPLIT_CURRENCIES = 2`**, in config, overridable. Three-way splits
  to fund one award are operationally absurd and multiply residue.
- `--max-stranded-points 0` keeps its v0 meaning: strict zero, which will reject
  most real transfers, and that is the user's call to make.
- **New output: the residue report.** After a whole trip is planned, print
  leftover balance per currency and flag any currency left with a balance too
  small to be useful. "This plan leaves 3,000 MR and 12,000 TY stranded" is a
  real cost the v0 output never showed.

### 4.7 Algorithm (v1 leg evaluation)

```
evaluate_leg(leg, wallet, transfer_date, ratios, surcharges):
    cash_side  = cheapest cash option + ALL mandatory fees (payable on cash)
    points_side = []

    for candidate in leg.points_candidates:
        P = normalize(candidate.program)
        if not is_partner_from_any(wallet.currencies, P, transfer_date):
            record NOT_A_PARTNER ; continue

        surcharge = surcharge.resolve(P, candidate.operating_carrier,
                                      region(leg), candidate.cabin,
                                      departure_country(leg), captured=candidate)

        plan = funding.best_plan(wallet, P, candidate.points, transfer_date)
        if plan is None:
            record BLOCKED (balance or stranding) ; continue

        fees = mandatory fees where payable_on_points
        if surcharge.is_known:
            score = plan.score_usd + surcharge.point + fees
            lo    = plan.score_usd + surcharge.low   + fees
            hi    = plan.score_usd + surcharge.high  + fees
        else:
            score = UNKNOWN
            break_even_surcharge = cash_side - plan.score_usd - fees

        points_side.append(...)

    best = pareto_front(points_side)  # on (points_score_usd, cash_out_of_pocket)
    verdict = compare(best, cash_side)
    if verdict flips anywhere in [lo, hi]:  mark VERDICT_SENSITIVE
    alternatives = alternatives.find(leg, best, surcharges, ratios)
    return LegResult(...)
```

`alternatives.find()` is the "book via Iberia, not BA" engine. For the winning
candidate's **operating carrier**, it looks up every other program that can
ticket that metal (`programs.yaml` → `bookable_carriers`), resolves each one's
surcharge, and emits an `Alternative` for any program with a materially lower
surcharge. If that program's award price is unknown — which it usually is — the
alternative is emitted as an **unpriced counterfactual with a break-even points
figure**: *"Aeroplan carries $0 YQ on this metal. If its award price is below
N points, it beats the BA option. Look it up."* It is never scored as if the
price were known. This reuses v0's break-even machinery rather than inventing a
second honesty mechanism.

## 5. Tech choices

Unchanged from v0 unless noted; the v0 stack was correct.

- **Python 3.11 + dataclasses + CSV/YAML + pytest + rich + requests.** No change.
  Rejected again: FastAPI (no server in scope), Pydantic (dataclasses plus the
  Step-7 validators are sufficient and add no dependency), asyncio (Seats.aero is
  rate-limited; sync is simpler), pandas (CSV tables are hundreds of rows).
- **CSV over SQLite for surcharges.** Rejected SQLite: the surcharge table will
  be low hundreds of rows, and a CSV is diffable in review — which matters
  enormously when every row is a claim about the world that someone has to check.
  Revisit only if the table passes ~2,000 rows.
- **A hand-written specificity matcher over a rules engine.** Rejected a generic
  rules DSL: five tiers, fixed order, ~30 lines. A DSL would make the
  most-specific-wins semantics harder to audit, and auditability is the point.
- **Typed `Reason` codes over free-text explanations.** Rejected logging-only:
  explanations that only exist as prose cannot be tested, and the v0 experience
  (a leg reporting "not a UR partner" when it was really blocked by the
  stranding constraint) shows how explanation bugs hide behaviour bugs.
- **Ranges over point estimates for surcharges.** Rejected single numbers: the
  research itself is a range ($600–1,000), and collapsing it to a midpoint
  manufactures a precision the underlying data does not have.
- **Recorded API fixtures over live tests.** Rejected hitting Seats.aero in CI:
  1,000 calls/day, and this sandbox cannot reach it at all. Record once on the
  Mac, replay forever.

### Step 2 — Runtime wallet

**Files**: `src/wallet.py`, `data/wallet.example.json`, `src/main.py`,

### Step 3 — Multi-currency ratio data  *(research + verification)*

**Files**: `data/ratios.csv`, `data/programs.yaml`, `tests/test_ratio_table.py`

Add Amex MR, Citi TY, Capital One, Bilt partner rows. Extend the CSV with
`source` and `verified_on` columns; backfill the existing UR rows.

be verified is omitted, not guessed** — the same standard that produced v0's UR

must be supplied per program; the tool must never assume the BA price applies to
Iberia.

test asserting every row has a non-empty source and a `verified_on` within the

## 8. Testing strategy (for the tester)

**Regression first.** All 118 v0 tests must pass at every step. Any test that
changes must be listed with a justification, exactly as v0 did for its six.

**Surcharge model**
- Specificity: the ex-GB BA row beats the generic BA row beats the generic
  program row. Assert the winner, and assert no blending.
- **Absence is unknown, not zero.** The highest-value test in the suite. Assert
  that an unmatched `(program, carrier)` never yields `0.0`, and that no code
  path substitutes a default.
- Ranges: a verdict that flips between `low` and `high` sets `VERDICT_SENSITIVE`
  and the recommendation is not presented as settled.
- Precedence: captured > modeled > unknown, including a captured $0 (real, e.g.
  a genuinely surcharge-free fare) which must **not** be confused with an
  unknown that happens to render as blank.
- Basis conversion: a one-way leg against a round-trip row halves and flags.
- Missing/assumed `operating_carrier` degrades to unknown and never resolves.

**Multi-currency**
- Single-currency results are byte-identical to v0 (golden-output test).
- Split funding: **stranding ≤ one block, not N blocks** (the R2 trap).
- No split when one currency suffices (R3); ties break to fewer currencies.
- `MAX_SPLIT_CURRENCIES` is respected.
- Absent currency ≠ zero balance ≠ unconstrained — three distinct behaviours,
  three tests.
- Per-currency valuations change the ranking; the default (all 1cpp) does not.
- Residue report reconciles exactly.

**Transfer date**
- The Oct 2026 Hyatt cliff on both sides, with travel in Jan 2027 — the case v0
  gets wrong.
- `TRANSFER_DATE_WINDOW` fires when a better ratio exists at another date.

**Hotels**
- Mandatory fees hit both the cash and the points total when
  `payable_on_points`; a fee that flips the verdict is pinned.
- Per-night × nights arithmetic, including a stay spanning a ratio change.
- No award price supplied → break-even, never a guess.
- Award-rule flags default off; enabling one without a source fails validation.

**Alternatives**
- The Avios family never shares a price across programs.
- No alternative is ever emitted with an invented points price.
- Zero-surcharge alternatives are emitted for BA-metal candidates.

**Honesty invariants — assert these as properties, over every fixture**
- `google_badge_unverified` is never rendered without its warning.
- A points figure with `source == "unknown"` never enters a total.
- An empty Seats.aero result never renders as "no availability" unless
  `last_error is None`.
- Every `Reason` attached to a rendered plan has a known code.
- **PAY CASH remains a first-class verdict** and its four sub-states (`cash`,
  `cash (no points path)`, `cash (points unpriced)`, `cash (points blocked)`)
  stay distinct. A fifth arrives in v1: `cash (surcharge unknown)`.

**Adversarial**
- Wallet with every balance `null`; wallet with all zeros; wallet with cards but
  no balances; unknown card; unknown currency; unknown IATA code; a hotel leg
  with zero nights; a negative surcharge in the CSV; duplicate surcharge rows at
  the same tier; a `verified_on` in the future.

## 10. Open risks

- **The wallet may make this moot.** If Tsuki holds only Chase cards, the
  multi-currency work is dead weight in v1 and the honest ordering is
  surcharges → hotels → multi-currency. Step 2 is cheap and comes first
  precisely so this can be discovered before Step 3's data work is done.
- **Surcharge data ages badly.** Carrier surcharges change without notice and
  the table has no refresh mechanism. Mitigation: `verified_on` on every row and
  a test that warns (not fails) past 180 days. A stale $800 is more dangerous
  than an unknown, because it looks confident.
- **Economy surcharges are the actual gap in Tsuki's real trip.** The research
  is business-cabin and both his BA legs are economy, so the flagship case
  resolves to *unknown*, not to a number. That is correct behaviour but it is
  not a satisfying answer, and it means the 16% headline gets replaced by a
  range rather than a corrected figure.
- **Seats.aero may not return operating carrier.** If it returns only marketing
  carrier, the surcharge model degrades to unknown on most live results, and the
  feature only works on manually captured candidates. Step 0 tells us. This is
  the largest single technical unknown in v1.
- **Rate limit.** 1,000 calls/day. Multi-currency does not increase call volume
  (funding is local), but alternatives-hunting across programs might if it ever
  triggers extra searches. It must not: `alternatives.find()` is a pure function
  of already-fetched data plus the local tables.
- **Regression risk in `funding.py`.** Extracting and generalising the one piece
  of code that carries the stranding constraint is where a silent
  multi-block-stranding bug will appear if it appears anywhere. Golden-output
  tests against v0 are the mitigation.
- **Scope.** Three features in one version is a lot. If it must be cut, cut
  **multi-currency** — it is the one whose value is entirely contingent on an
  unanswered question (§9.1), while surcharges fix a known-wrong number and
  hotels fix a known-missing cost.

## 11. The three decisions most likely to be wrong

**1. Modeling surcharges from a static table rather than reading them per
booking.**
The table is a generalisation over a fee structure that is genuinely
per-itinerary: it varies by fare construction, by routing, by connection point,
by taxes that change with the calendar. A $600–1,000 band for "BA business
transatlantic" may be wide enough to be useless for a specific decision — and if
the band spans the verdict, `VERDICT_SENSITIVE` fires and the tool declines to
recommend, which is honest but unhelpful. If Step 0 shows Seats.aero returns
real per-flight taxes, **the table should demote to a fallback for manually
captured candidates and the whole of §4.3 shrinks**. It is designed to allow
that (captured > modeled > unknown), but the effort split between building the
table and validating the API may turn out backwards.

**2. Bounding split funding at two currencies with a greedy fill.**
R2's "only the last transfer carries slack" is a heuristic, not an optimum. A
genuinely optimal multi-currency funding plan is a small integer program, and
there will be cases — unusual ratios, an active bonus on one currency, a nearly
exhausted balance — where greedy fill picks a plan that strands more or costs
more than the true optimum. The bound is defensible on operational grounds
(three-way splits to fund one award are absurd) but it is a design choice made
for simplicity, not for correctness, and it should be revisited the moment a
real wallet produces a case where the greedy answer is visibly wrong.

**3. Hotels by manual entry.**
This is the honest design given no API, but it may be the wrong *feature*.
Manual entry means the user has already done the hard part — found the award and
read its price — before the tool does anything. What is left is arithmetic the
user could do in their head. If the real value of a hotel feature is
*discovery* ("where can I get outsized value with these points?"), then v1's
hotel work delivers almost none of it, and the effort would be better spent on
the surcharge feature, which genuinely sees something a person cannot easily see.
**This is question §9.3 and Tsuki should answer it before Step 10 starts.**
