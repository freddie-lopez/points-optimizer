## 1. Summary

v3 made a trip scoreable against live availability. The pre-v5 round made the
tool honest about the seven ways it can fail to know something. What is still
missing is everything around that: a live number cannot be *re-derived* by anyone
but the person who ran it, a new trip cannot be *entered* without hand-writing
JSON, the API key can only be found in one place, live is opt-in when it is the
actual mode of use, and a UK departure tax that is landed, loaded, tested and
deliberately unwired still silently misses from every LHR-departure score.

The five sentences v5 must be able to say and v4 structurally cannot:

> **"Trip B beats cash by X% — replayed from manifest `mh_8f3c…a91d`
> (7 snapshots, all present, all hashes match). Anyone with this repo gets this
> exact number."**

> **"I entered a new trip in one command, and the tool refused to let me put a
> points price in it, so the only way it can ever be scored is live."**

> **"Key from `~/.config/points-optimizer/.env` (`pro_…jwV`)."**

> **"You asked for a score, there is no network, and I have neither guessed nor
> quietly fallen back to a badge. Exit 3."**

> **"LHR→SFO owes £102 APD per passenger on top of the carrier surcharge — and
> on the live path I have NOT added it, because nobody has yet checked whether
> Seats.aero's `TotalTaxes` already contains it."**

v5 adds no new programs, no cash API, no productization, and — with the single,
fenced exception of item 5 — no new scoring logic.

## 2. Assumptions & decisions

### Settled — do not re-derive

- **Scope is UR-only.** Tsuki holds a Chase Sapphire Preferred and an Amex Hilton
  Surpass; `data/ratios.csv` is 18 UR rows. UR balance 160,000. No v5 step
  populates MR rows or touches the multi-currency engine. The Manager's decision
  3 stands at option (a): leave it, it costs nothing at runtime.
- **`evaluate_leg`, the Seats.aero parser, and surcharge resolution are
  off-limits.** Every step below states its own compliance with this line. The
  single exception is Step 7, which adds an *additive* term outside the surcharge
  resolution path and never inside it.
- **The exhaustive list on `LiveLegOutcome` is the contract.** Seven numbered
  ways across five axes, each a field with a `raise` and an unconditional
  `render()` clause. v5 adds an **eighth** (§4.3) and adds it the way the
  docstring's "HOW TO EXTEND THIS" says to: a field, a raise, an unconditional
  clause, a numbered entry. Not a branch inside a renderer.
- **Absence is never zero.** `apd.lookup()` returns `None`, never `0.0`, and v5
  keeps it that way. A departure this table does not cover is a departure whose
  tax is UNKNOWN.
- **Live mode owns the points side; the fixture owns the cash side, forever.**
  There is no cash-price API in v5 either.
- **Only an award on the leg's own date is scored** (v3 §4.5). Unchanged.
- **The 1,000 calls/day Pro cap is real.** Live-by-default raises exposure to it;
  see §9.

### New decisions for v5

- **A quotable margin is quoted against a manifest hash, not against a clock.**
  The Manager's design note is binding. `--from-snapshot` makes the manifest an
  *input*, and the percentage and the hash are emitted by the same call — the one
  structural defence in this codebase that has actually worked.
- **A replayed run is never `live`.** `margin_provenance` gains a fourth value,
  `snapshot`. `--require-all-live` (now the default) is satisfied by `snapshot`
  **only when every replayed leg was `live` at capture time**; a manifest whose
  rows record a badge fallback replays as a badge fallback. Replay reproduces a
  number; it does not launder it.
- **`--from-snapshot` refuses more than it repairs.** A missing snapshot, a
  content hash that does not match the bytes, or a manifest that does not cover
  every queryable leg is a hard refusal before anything is scored (exit 1). There
  is no "replay what we have" mode. Partial replay is how a reproducible number
  becomes an irreproducible one wearing a hash.
- **A fixture built by `--new-trip` cannot carry a points price.** The builder
  writes no `points_candidates`, ever, and the loader is not changed to make that
  easier — the refusal is in the builder and is tested by reading the file back.
  A hand-written badge number is exactly the thing v3 existed to stop quoting.
- **Live is the default; offline is the exception.** `--offline` and
  `--allow-badge-fallback` are the opt-outs. A run with neither network nor
  `--offline` fails loudly with the exit-3 withhold. There is no silent fallback
  path in v5 and adding one is a regression, not a convenience.
- **APD is a separate table, additive, program-independent, and applied on the
  offline path only until one live LHR row settles the question.** `data/apd.csv`
  stays its own file with its own loader (the pre-v5 reasoning is correct: a
  government departure tax and a carrier YQ are different quantities, and merging
  them is how "United charges no YQ" becomes "this leg costs nothing in cash").
- **APD band resolution is data, not arithmetic.** HMRC bands by distance from
  London to the *destination country's capital*. Nothing in this repo knows a
  capital or a distance. v5 adds `data/apd_bands.csv` (country → band, with the
  capital and the distance that justified it, sourced and dated) rather than
  computing a great-circle distance to an invented coordinate. An unlisted
  country resolves to `None`, which is UNKNOWN, which is not band A.

### 4.2 The replay seam

`--from-snapshot` does **not** get its own scoring path. It substitutes the
transport underneath `search_raw` and nothing else:

```
--live       : query_leg -> client.search_raw -> HTTP (or disk cache)
--from-snapshot : query_leg -> SnapshotTransport.search_raw -> committed file
--offline    : query_leg not called; NOT_QUERIED with a stated reason
```

Everything downstream — parse, `award_to_candidate`, `_record`, `apply_live`,
`evaluate_trip`, the formatter — is byte-identical across the three. That is the
property Step 2's acceptance test asserts directly: a replay of the manifest
written by a live run reproduces that run's per-leg table exactly, modulo the
provenance line and the replay banner.

Consequences that fall out of the seam and must not be worked around:

- **`--from-snapshot` and `--live` are mutually exclusive.** Both name a
  transport. Passing both is a usage error (exit 1) with a message that says
  which one to drop and why, checked in `main()` before dispatch alongside the
  existing `--live requires --trip-fixture` check.
- **The response cache is bypassed entirely.** No `get`, no `put`, no snapshot
  archival, no manifest row. A replay must not append to the manifest it is
  replaying — that is a file writing itself, and the hash of the input would
  change while it is being read. `ResponseCache` is not passed to `LiveOptions`
  on the replay path at all, so this is structural, not a flag check.
- **`--refresh`, `--cache-ttl` and `--flex-days` are rejected with
  `--from-snapshot`,** not silently ignored. The first two name cache behaviour
  that does not exist here; the third would change the request key and therefore
  ask for a snapshot that was never captured. Silently ignoring a flag that
  changes the answer is this project's failure mode in miniature.

### 4.3 The eighth way to fail to know

`--from-snapshot` introduces a genuinely new epistemic state and it gets the full
treatment the `LiveLegOutcome` docstring demands. Appended to AXIS 5:

> **(8) The bytes are a replay of a COMMITTED SNAPSHOT, not of the API.** We did
> not ask anyone anything on this run. → fields `replayed_from_snapshot`,
> `snapshot_name`, `snapshot_content_hash`, `snapshot_captured_at`,
> `snapshot_parser_version`.
> **INVARIANT**: `replayed_from_snapshot` with no `snapshot_content_hash` raises.
> `replayed_from_snapshot` together with `served_from_cache` raises — the bytes
> came from one place and the outcome must say which. `provenance` may never be
> `PointsProvenance.LIVE` on a replayed outcome; it is `SNAPSHOT`.
> A `_replay_clause()` is appended to **every** render unconditionally, naming
> the snapshot file and its capture time, so no reader can mistake a replayed
> observation of January for a fresh one.

`is_a_finding_about_award_space` stays a whitelist. `SNAPSHOT` is added to it
deliberately and with the reason written down: a snapshot's emptiness *was* a
finding at capture time, and replay preserves findings — including
`ANSWERED_INCOMPLETE`, which replays as `ANSWERED_INCOMPLETE`, because the
truncation was a property of the bytes.

### 4.4 Manifest format, and what the hash is over

Today's `MANIFEST.md` is an append-only markdown log, one row per fetch, filled
in by `annotate_manifest` once parsing is done. v5 keeps that file and that
format — it is human-readable and already written by the one event that writes a
snapshot — and adds three things.

**(a) Three columns.** `content_hash` (short, 16 hex), `parser_version`, and
`trip_id`. `parser_version` is a new `seats_client.PARSER_VERSION` constant
stamped into `_meta` at `put` time. Rows written before v5 have none; that reads
as `unknown` and is reported as such, never as "matches".

**(b) A selection rule, because the log has duplicates by design.** For a run of
trip `T`, the replay set is: rows with `trip_id == T`, grouped by
`(leg_id, route, dates)`, taking the row with the **latest `fetched_at`** in each
group. Stated in one place, in `snapshot_replay.py`, and printed as part of the
replay banner ("7 rows considered, 7 groups, 7 selected, 0 superseded").

**(c) The manifest content hash — what a margin is quoted against.**

```
manifest_hash = sha256( "\n".join(sorted(
    f"{leg_id}|{route}|{dates}|{snapshot_name}|{recomputed_content_hash}"
    for each SELECTED row
)) )
```

Three properties this shape buys, each deliberate:

- It is over the **selected replay set's content**, not over the markdown bytes.
  Fixing a typo in the manifest's prose does not invalidate a quoted number;
  changing one byte of one snapshot does.
- `recomputed_content_hash` is `content_hash(pages)` **recomputed from the file
  on disk**, not read from `_meta`. A tampered snapshot whose `_meta` was edited
  to match is caught by the mismatch between the two; a tampered snapshot whose
  `_meta` was *not* edited is caught the same way. There is no way to alter the
  bytes and keep the hash without also altering the hash.
- Sorted, so row order in the log cannot change a quoted number.

Printed as `mh_` + first 16 hex, e.g. `mh_8f3ca91d5b2e4470`, **on the same line
as the percentage**, by the same call. `print_trip_totals` is where this happens;
a margin string produced anywhere else in a replay run is a bug.

### 4.5 `--new-trip`: what it may and may not write

The builder emits a `TripFixture`-shaped JSON with `legs[]`, and for each flight
leg: `id`, `kind: "flight"`, `description`, `date`, `origin`, `destination`,
`travelers`, `cabin`, and exactly one `cash_options` entry (label, amount,
currency USD, `source: "user_entered_via_new_trip"`, `captured_on: <today>`,
`date: <leg date>`). Hotels get `kind: "hotel"`, `nights`, `travelers`, one cash
option, and **no** `origin`/`destination` (Seats.aero is flights-only; a hotel
leg with codes would be queried).

Three refusals, each with a cautionary tale behind it:

1. **No `points_candidates` key is written at all** — not an empty list with a
   comment, not a placeholder. The file is therefore only scoreable live, which
   is the whole point. A `trip_level_flags` entry says so in the fixture itself,
   so the refusal survives being read by a human six months later.
2. **`origin`/`destination` are set from the flags, and the description is
   *generated from the codes*** — `"SFO->MAD, Jan 15 2027, one-way, economy,
   1 adult"`. Trip B's B1 says MRY→MAD and is coded SFO→MAD, and that drift
   survived four versions because the description was written by a human and the
   code by another human on a different day. The builder never lets them
   disagree because only one of them is input.
3. **Unknown IATA codes are refused, not passed through.** Validated against
   `data/airports.csv` via `regions.airport()`, which already raises with a
   message about wrong regions selecting wrong surcharge bands. The builder
   catches it and re-raises naming the offending flag and listing nothing — it
   does not suggest a "did you mean", because a near-miss suggestion on an
   airport code is how MRY becomes SFO.

`surcharge_currency` is only written when a surcharge is actually captured, and
then it is written explicitly. MR-2 made an unpriceable captured surcharge a
per-leg UNKNOWN rather than a dead run, so this is now safe to emit — but the
builder still defaults to writing no surcharge at all rather than writing
`0.0` with no flag, because `cash_surcharge: 0.0` with no flag is silence.

### 4.6 APD wiring, and the double-charge trap

The rule, from `docs/research/surcharge-and-apd-data.md`: APD is charged on
**departure from a UK airport only**, on award tickets too, by every carrier and
every program, additive to the carrier surcharge, keyed on
`(departure_country=GB, band-by-destination-capital, cabin-class, departure date)`,
**per passenger**.

```
leg departs GB?  -- no  --> nothing. Not zero: nothing. No field set.
      |
     yes
      v
band = apd_bands.lookup(country_of(destination))     # None -> UNKNOWN, stop
rate = apd.lookup("GB", band, cabin_class, leg.date) # None -> UNKNOWN, stop
apd_usd = convert_to_usd(rate.rate * travelers, "GBP")
      |
      +-- offline / badge leg  --> ADD to the leg's points-side cash total,
      |                            disclosed as its own line with the GOV.UK
      |                            source and the band that was chosen.
      |
      +-- live / snapshot leg  --> DO NOT ADD. Set `apd_inclusion_unverified`
                                   with the amount, and render:
                                   "This leg departs the UK and owes GBP X APD
                                    per passenger. It is NOT added here: this
                                    leg's cash figure came from Seats.aero's
                                    TotalTaxes and NOBODY HAS CHECKED whether
                                    that field already includes APD. Adding it
                                    would risk double-charging; omitting it
                                    risks understating. The figure is stated so
                                    you can check it against a booking page."
```

The asymmetry is the design, not a gap. On the offline path the tool owns the
whole cash figure and knows APD is missing from it. On the live path the tool
does not know what is inside `TotalTaxes`, and a guess in either direction
produces a confident wrong number. Stating the amount without applying it is the
only honest third option, and it converts the unknown into a **one-row
experiment Tsuki can run** (Step 8).

`cabin_class` mapping: `Y` → `reduced`; `W`, `J`, `F` → `standard`. HMRC's actual
test is seat pitch ≥ 40in, not cabin name, so a premium-economy cabin below that
pitch is legally reduced-rate. The mapping is written in one place with that
caveat in the note that prints, and W is the row to revisit first.

**Compliance with the off-limits line**: Step 7 touches `optimizer` at exactly
one place — an additive term on the offline points-side total, after
`evaluate_leg` has selected a candidate. `evaluate_leg`'s own logic, the parser,
and `SurchargeTable.resolve*` are not read, not called differently, and not
modified. APD never enters the surcharge table, never becomes a surcharge row,
and never participates in captured-beats-table precedence.

### 4.7 Key resolution

```
--api-key <k>                        -> provenance "flag"
SEATS_AERO_KEY in os.environ         -> provenance "env"
./.env                               -> provenance "repo .env"
~/.config/points-optimizer/.env      -> provenance "user config"
none of the above                    -> hard error, all four locations named
```

First hit wins; later sources are not consulted. `config.load_env` today is
hard-coded to the repo path and runs at import; v5 keeps that call (so existing
behaviour is unchanged) and adds the user-config path after it, then adds
`resolve_key() -> (key, source)` as the single accessor. Every live, replay-with-
network-check, or single-route run prints one line:

```
Seats.aero key: pro_…jwV   (source: user config ~/.config/points-optimizer/.env)
```

Masking is first 4 + `…` + last 3, and the masking function is the **only** thing
that ever formats a key. `assert_no_key_material` already guards cache and
snapshot writes; a test asserts the masked form is not sufficient to reconstruct
anything and that the full key appears in no printed output on any code path.

## 5. Tech choices, with what was rejected

| Choice | Rejected alternative | Why |
|---|---|---|
| Manifest stays markdown; hash is over selected rows' content | A machine-readable `MANIFEST.json` sidecar | Two files that can disagree is worse than one file that a parser has to work slightly harder to read. The markdown log is already written by the one event that writes a snapshot, and it is reviewable by a human, which is the only reason it exists. |
| Recompute `content_hash` from the file, compare to `_meta` | Trust `_meta.content_hash` | Trusting the file's own claim about itself makes tampering a two-line edit. Recomputing makes it impossible. |
| Refuse a manifest with any missing/mismatched snapshot | Replay what exists, flag the rest | A partially-replayed margin is not reproducible, and it would be printed next to a hash, which is worse than printing it next to nothing. |
| Parser-version drift REPARSES and warns | Refuse to replay a stale snapshot | Storing raw bytes exists precisely so a parser fix is re-runnable against yesterday's responses. Refusing would delete that property. The warning is prominent and the version pair is printed with the hash. |
| `--new-trip` writes no `points_candidates` key at all | Write `[]` | An empty list is a thing a future editor fills in. A missing key plus a `trip_level_flags` sentence is a decision. |
| `data/apd_bands.csv` (country → band, sourced) | Great-circle distance from airport coordinates | HMRC bands by capital city, not by airport. Computing a distance to a coordinate this repo does not have, and then band-ing it, is inventing two facts to derive a third. |
| `--offline` as an explicit opt-out | Auto-detecting no network and falling back | Auto-fallback is the failure-as-finding class with a different subject. |
| Interactive `--new-trip` via `input()` | `prompt_toolkit` / `questionary` | No new dependency for a prompt loop. `requirements.txt` stays at three lines. Interactive mode is untested-by-hand-only otherwise; a thin `_prompt()` seam makes it scriptable in tests. |
| `PointsProvenance.SNAPSHOT` as a fourth value | Reusing `LIVE` with a flag | The margin provenance string is what gets quoted. A replayed number that calls itself live is the exact laundering this feature exists to prevent. |

### Step 2 — Manifest v2: three columns, parser version, and the content hash

**Files**: `src/response_cache.py`, `src/seats_client.py`,
`src/snapshot_replay.py` (new), `tests/test_snapshot_manifest.py` (new)

Add `PARSER_VERSION` to `seats_client` and stamp it into `_meta` at `put`. Add
`content_hash` (16 hex), `parser_version` and `trip_id` columns to the manifest
row and header. Write `snapshot_replay.py` with, and only with:
`parse_manifest(path) -> [ManifestRow]`, `select_replay_set(rows, trip_id)`,
`verify(rows) -> [Problem]`, `manifest_hash(selected) -> str`.

**Off-limits compliance**: `response_cache` gains columns; the parser is not
touched and `search()` is unchanged. Nothing is scored in this step.

**Acceptance**:
- Round trip: a `put` writes a row whose `content_hash` column matches
  `content_hash(pages)` recomputed from the archived file.
- Rows written before v5 (no `content_hash`/`parser_version` columns) parse into
  `ManifestRow` with those fields as `None` and are reported as `unknown`, not
  as matching.
- Selection: a manifest with two rows for the same `(leg, route, dates)` selects
  the later `fetched_at` and reports the other as superseded; a re-fetch row
  marked "(re-fetch, identical)" pointing at the same file does not double-count.
- `manifest_hash` is invariant under row reordering and under edits to the
  manifest's prose header; it changes when any selected snapshot's bytes change
  by one character.
- `verify` returns a named problem for: file missing on disk; recomputed content
  hash ≠ `_meta` hash; recomputed content hash ≠ manifest column; snapshot not
  loadable as an envelope.
- Built against the one real snapshot plus synthetic ones: a test constructs a
  three-row manifest from `sfo_mad_real.json` and two synthesised envelopes and
  hashes it deterministically.

### Step 3 — `--from-snapshot` replay, and way (8) on `LiveLegOutcome`

**Files**: `src/models.py`, `src/live_trip.py`, `src/main.py`,
`src/formatter.py`, `tests/test_from_snapshot.py` (new)

Add the four replay fields and their invariants (§4.3), the numbered entry (8) in
the docstring, `_replay_clause()` appended unconditionally to `render()`, and
`PointsProvenance.SNAPSHOT`. Add `SnapshotTransport` in `snapshot_replay.py`
exposing the same `search_raw` shape the client does, so `query_leg` does not
learn a new branch — it gets a different object. Add `--from-snapshot <manifest>`
to the CLI, mutually exclusive with `--live` / `--offline` / `--refresh` /
`--cache-ttl` / `--flex-days`, checked in `main()` before dispatch. `LiveOptions`
gets `cache=None` on this path structurally.

**`LiveLegOutcome` failure axes this step can hit**, and the handling of each —
this is the step that produces a number, so all eight are answered:

| Axis / way | On the replay path | Handling |
|---|---|---|
| (1) never asked | A leg with no snapshot row | **Refuses the whole run** at verify time, exit 1. Never a `NOT_QUERIED` inside a hashed run. |
| (2) transport failed | Cannot occur — no transport | If the *snapshot itself* records an API_ERROR, it replays as `API_ERROR` with the original message plus the replay clause. |
| (3) budget exhausted | Cannot occur — no calls made | A snapshot recording `BUDGET_EXHAUSTED` is refused at verify: a budget failure was never archived (finding H-1), so a row claiming one is a corrupt manifest. |
| (4)(5) unreadable / envelope disagreement | Fully live — the bytes are re-parsed by the current parser | Replays as `ANSWERED_UNREADABLE`. If a *parser upgrade* makes previously-unreadable rows readable, the count changes and the banner says the parser version differs. This is the feature working. |
| (6) truncated | Preserved from the bytes | `result_incomplete` is recomputed from the archived pages, not copied from `_meta`. `ANSWERED_INCOMPLETE` replays as itself. |
| (7) served from cache | Forbidden | `replayed_from_snapshot` + `served_from_cache` raises. Cache is not constructed on this path. |
| (8) replayed | Always true here | `provenance = SNAPSHOT`; margin provenance `snapshot`; hash printed with the percentage. |

**Off-limits compliance**: `query_leg`'s branch structure, `award_to_candidate`,
`_record`, `evaluate_leg` and the parser are unchanged. The transport object is

**Acceptance**:
- `--from-snapshot M --live` and `--from-snapshot M --offline` each exit 1 with a
  message naming both flags and saying which to drop.
- A manifest whose every snapshot is present replays and prints
  `margin X.XX%–Y.YY%  |  manifest mh_… (N snapshots, parser vA at capture / vB

  adjacent in the rendered output and that the percentage never appears in any

  offering to update it.

  unchanged by the reparse (it is over bytes, not over awards).
- The cache is never written: after a replay, `data/cache/` mtime is unchanged
  and no new manifest row exists. Asserted by file listing, not by a mock.
- Two replays of the same manifest six hours apart produce byte-identical output
  except for the wall-clock line. This is the property the whole feature is for.
- Replay of a manifest whose rows record `badge_fallback` yields margin
  provenance `badge_fallback`, **not** `snapshot`, and under the (now default)

invariants above. Anything else red is a v5 bug, not a test to update.

## 9. Open risks

1. **Live-by-default multiplies API spend.** `test_B7b`'s known case — a server
   returning the same cursor forever spends 25 calls on one leg — was "fine for
   now" when live was opt-in. After Step 6 it is the default. Four legs × 25 =
   100 calls, 10% of the daily cap, from one accidental run. Mitigation: none in
   v5 beyond the existing cap. Named so it is not a surprise.
2. **`--from-snapshot` makes a stale number *easier* to quote.** The hash proves
   reproducibility, not currency. A January manifest replays perfectly in June and
   prints a confident percentage. The `_replay_clause()` names the capture date on
   every leg and the banner names it once more, but there is no expiry and adding
   one would reintroduce the TTL mistake v3 §11.3 identified. This is a
   deliberate trade and it can bite.
3. **The manifest is append-only and unbounded.** After a hundred live runs, the
   selection rule does real work and a wrong selection silently changes a hash.
   Step 2's superseded-row reporting is the mitigation; it is a report, not a
   guard.
4. **APD's offline/live asymmetry means the same trip scores differently in two
   modes on purpose.** Offline B4 will report ~$64 saving; live B4 will report
   ~$202 with a flag. A reader who compares the two without reading the flag sees
   an inconsistency. Unavoidable until Step 8 runs, and it is the honest shape,
   but it is a genuinely confusing output and Step 8 should be run early.
5. **`~/.config/points-optimizer/.env` is a new place a key can live and a new
   place it can leak.** It is outside the repo so gitignore does not protect it.
   The banner prints only the mask; nothing writes to that path.
6. **`--new-trip` writes into `tests/fixtures/trips/`,** which is a *test*
   directory that is now also a user-data directory. A user-built fixture that
   fails to load will break the test suite for reasons that have nothing to do
   with the code. Mitigation: the builder validates by loading the file back
   before reporting success, so a broken fixture is never left behind.
7. **Trip B's traveler question (§8.1) blocks a correct APD figure.** APD is per
   passenger. If the trip is for two, every APD number in this plan doubles.

## 10. The three decisions most likely to be wrong

**1. Refusing to replay a manifest whose snapshots are not all present.**
The argument is that a partial replay produces an irreproducible number printed
next to a hash, which is worse than no hash. But the common case in six months
will be a manifest with nine good rows and one snapshot someone deleted while
tidying, and the tool will refuse to produce anything at all. A user who wants a
number will delete the row, or the manifest, and re-run live — which is exactly
the "route around the guard" failure v3 §11.2 predicted for off-date awards and
which may already have come true there. If that happens, the honest answer is
probably a *second* hash: one over the legs that replayed and one naming the legs
that did not, with the percentage refused but the per-leg table printed. That is
more machinery than v5 should carry on a guess, so the refusal ships — but it is
the first thing to revisit if Tsuki ever says "it just told me no again".

**2. Adding APD offline but only flagging it live.**
This is the design I am least comfortable with, because it means the tool's most
trusted mode (live) is the one that reports a number it *knows* is missing a
£102 charge, while the mode we call an exception reports the complete one. The
justification — you cannot add to a figure whose contents are unknown without
risking a double charge — is sound. But the *effect* is that live Trip B keeps
reporting a $202 saving that is probably $64, and reports it with a live
provenance line next to it, which is the most credible-looking wrong number this
tool can produce. If Step 8 is going to slip, the safer shape is to **withhold
the B4 leg's points verdict entirely on the live path** rather than report an
un-APD'd one with a flag, and take the coverage loss. I chose the flag because
withholding a leg over an unverified tax would have been the tool refusing to
answer over a question it invented. I am about 60/40 on it.

**3. Making `--require-all-live` the default while `--from-snapshot` exists.**
These two features push in opposite directions and I have not fully reconciled
them. `--require-all-live` says "withhold unless everything is fresh";
`--from-snapshot` says "here is a number from January and it is exactly
reproducible". The plan resolves this by making `snapshot` satisfy the
requirement when every replayed leg was live at capture — but that means the
default flag, whose entire purpose is to stop a stale or mixed number being
quoted, is satisfied by bytes of arbitrary age. If someone quotes a replayed
number in April from a January capture and calls it "all live", the default did
not do its job, and the `_replay_clause()` will be the only thing standing
between them and a wrong claim. The alternative — `--require-all-live` refusing
replays outright — would make the flagship reproducibility feature unusable under
the default, which is worse. If this is wrong, the fix is a third exit code or an
age threshold on replay, and I would rather see it fail once than guess the
threshold now.
